# MoneyVerse — Integration Guide for the Four Game Teams

## How your game plugs into the app

This guide explains how each game connects to the MoneyVerse application, what the host provides, how game results are processed, and what each team is responsible for.

It is written for developers who have not participated in the original planning discussions.

**Important:** This document describes the current repository implementation on `main`. Some planned integration conventions are not yet implemented. Follow the current contract below unless the shell owner explicitly approves a change.

---

# 1. The 60-second version

MoneyVerse has four financial-learning pillars:

| Pillar | Current game | Current location |
|---|---|---|
| Plan & Budget | Festival Showdown | `src/games/showdown/` |
| Save & Manage | Pocket Panic | `src/games/cafe/` |
| Understand Investing | Deal Board | `src/games/dealboard/` |
| Stay Financially Safe | Case Files: Mohalla Detective | `src/pillar4/` |

The shell has a game registry at:

`src/host/registry.ts`

It decides which game component to load for each pillar. The current games are integrated through host-side wrappers:

`src/host/wrappers/`

The wrapper translates between the application's common game interface and the individual game's existing component interface.

**Do not rename game folders, change the registry, modify wrappers, or edit shared host files without coordinating with the shell owner.**

Each team should primarily work inside its own game folder.

# 3. The shared GameProps contract

The common interface is defined in:

`src/host/types.ts`

Current interface:

```ts
export interface GameProps {
  seed: string
  cohortCode: string | null
  lang: Lang

  festival?: Festival
  avatar?: Avatar
  level?: 'beginner' | 'confident'

  classCode?: string | null
  installId?: string

  onComplete: (payload: unknown) => void
  onExit?: () => void
}
```

### What each property means

| Property | Purpose |
|---|---|
| `seed` | Stable seed generated by the host for the player and pillar |
| `cohortCode` | Teacher/NGO class code, or `null` |
| `lang` | Current application language |
| `festival` | Festival selected by the player |
| `avatar` | Player avatar selection |
| `level` | Difficulty preference |
| `classCode` | Alias for the class code |
| `installId` | Random installation identifier |
| `onComplete` | Sends the game's final result to the shell |
| `onExit` | Optional host exit callback |

Use only the properties your game needs.

### Language support: important current limitation

The current application defines:

```ts
export type Lang = 'en'
```

in `src/content/data.ts`.

Therefore, the application currently exposes English only. Do not assume that Hindi and Telugu are already supported by the shell.

If your game has additional translations, you can keep them internally, but the host currently supplies only the language value defined by the application.

### Defaults

The host currently supplies:

```ts
export const HOST_DEFAULTS = {
  level: 'beginner',
}
```

The default festival and avatar are defined in `src/content/data.ts`.

# 4. How games are mounted

The game registry supports two integration approaches:

1. A standard `index.tsx` game entry point.
2. An existing game component loaded through a host wrapper.

The current games mostly use the second approach.

The registry looks for a standard entry point first. If one is not found, it checks the configured component entry and loads its wrapper.

The current mapping is defined in `src/host/config.ts`:

```ts
export const GAME_FOLDERS = {
  plan: 'showdown',
  save: 'cafe',
  invest: 'dealboard',
  safe: 'casefiles',
}
```

The current component entries are:

```ts
export const GAME_ENTRIES = {
  plan: { file: 'ShowdownGame' },
  save: { file: 'PocketPanic' },
  invest: { file: 'ui/DealBoard' },
  safe: { file: 'Pillar4' },
}
```

The fourth pillar is a special case: its implementation lives in `src/pillar4/`, not in `src/games/casefiles/`.

**Do not create a duplicate Case Files implementation in `src/games/casefiles/` without discussing it with the shell owner.**

# 5. Game-specific integration contracts

## 5.1 Festival Showdown — Plan & Budget

**Location:** `src/games/showdown/ShowdownGame.tsx`

**Wrapper:** `src/host/wrappers/FestivalGame.tsx`

**Adapter:** `src/host/adapters/festival.ts`

The game currently exposes its own component interface:

```ts
interface ShowdownProps {
  cohortCode?: string
  onComplete?: (result: GameResult) => void
  onExit: () => void
  embedded?: boolean
}
```

The wrapper handles the translation from the shell's `GameProps` to these props.

### Completion behaviour

When the report is displayed, the game sends its result through `onComplete`.

The wrapper:

- Prevents duplicate completion callbacks.
- Saves the game result.
- Sends the result to the shell.
- Treats an early exit as a quit.

The wrapper currently does not pass the host's seed or festival into the game. Festival Showdown manages its own game state.

### Result format

Festival Showdown has its own result structure. The adapter supports multiple historical and current formats.

The current Showdown-specific format includes:

```ts
{
  score: {
    goals: number,
    onTime: number,
    resilience: number,
    smart: number,
    total: number
  },

  stars: {
    goals: boolean,
    onTime: boolean,
    resilient: boolean,
    cleanBooks: boolean
  },

  evidence: {
    // Game-specific evidence fields
  },

  minaretLit: boolean
}
```

The adapter also supports the older Festival Countdown format:

```ts
{
  game: 'festival',
  cohortCode: string | null,
  seed: string,
  festival: string,

  stars: {
    ghar: boolean,
    gift: boolean,
    dost: boolean,
    plan: boolean
  },

  score: {
    needs: number,
    plan: number,
    shopping: number,
    goal: number,
    balance: number,
    total: number
  },

  evidence: {
    // Optional evidence
  },

  lessonsSeen: string[]
}
```

### Current result mapping

For the Showdown-specific score:

| Game score | Shell skill |
|---|---|
| `goals` | Prioritising |
| `onTime` | Planning |
| `resilience` | Risk sense |
| `smart` | Scam sense |

Each component is normalised to a 0–1 skill score.

The adapter uses `minaretLit` when supplied. Otherwise, it evaluates the available stars and total score.

## 5.2 Pocket Panic — Save & Manage

**Location:** `src/games/cafe/`

**Wrapper:** `src/host/wrappers/PocketPanicGame.tsx`

**Adapter:** `src/host/adapters/cafe.ts`

**Important naming clarification:** The current Save & Manage game is Pocket Panic. Pay Run is an older game implementation and is not the currently configured Save pillar.

The wrapper mounts Pocket Panic and supplies:

```ts
interface PocketPanicProps {
  cohortCode?: string
  onComplete: (result: GameResult) => void
  onExit: () => void
}
```

The game manages its own saved month and progress. The wrapper does not pass the host seed into it.

### Completion behaviour

When the Tally/result appears, Pocket Panic sends its result to the wrapper.

If the player exits before completing the run, the wrapper sends:

```ts
{
  game: 'cafe',
  progress: 0
}
```

The wrapper ensures that completion is sent only once.

### Result format

Pocket Panic reports its own game result:

```ts
{
  game: 'cafe',

  score: {
    balance: number,
    saved: number,
    behaviours: number,
    total: number
  },

  evidence: {
    // Behaviour and decision evidence
  },

  lessonsSeen: string[],
  minaretLit: boolean,

  meta: {
    // Game-specific result metadata
  }
}
```

The exact evidence fields should follow the existing Pocket Panic implementation and its adapter.

### Legacy Pay Run compatibility

The repository still contains:

`src/games/payrun/`

and:

`src/host/adapters/payrun.ts`

The Pay Run adapter accepts the older payload shape:

```ts
{
  game: 'payrun',
  cohortCode: string | null,
  seed: string,

  shifts: number,
  goalReached: boolean,

  parts: {
    saving: number,
    buffer: number,
    spending: number,
    planning: number,
    lending: number
  },

  jar?: number,
  goal?: number,

  counters?: {
    purchasesBought: number,
    purchasesSkipped: number,
    friendsLent: number
  },

  lessonsSeen: string[]
}
```

Accepted aliases include:

- `habitScore`
- `habit`
- `scoreParts`
- `savingHabit`
- `spendingControl`
- `habitTotal`

The shell's Save adapter selects the Pay Run adapter for payloads with `game: 'payrun'`; other payloads go through the Pocket Panic adapter.

Do not assume Pay Run is the active Save game just because its folder and adapter still exist.

## 5.3 Deal Board — Understand Investing

**Location:** `src/games/dealboard/`

**Component:** `src/games/dealboard/ui/DealBoard`

**Wrapper:** `src/host/wrappers/DealBoardGame.tsx`

**Adapter:** `src/host/adapters/dealboard.ts`

The wrapper passes the host seed to Deal Board:

```tsx
<DealBoard
  seed={seed}
  onExit={exit}
  onComplete={done}
/>
```

Deal Board reports its score when its report screen appears.

The wrapper constructs the outgoing payload field by field:

```ts
{
  game: 'dealboard',
  mode: 'lite',

  judgement: score.total,

  skills: {
    research: score.research,
    skepticism: score.skepticism,
    spread: score.spread,
    calm: score.calm,
    habits: score.habits
  },

  counters: {
    trapsAvoided: score.counters.trapsAvoided,
    prematureSells: score.counters.prematureSells,
    fees: score.counters.feesPaid,
    concentrationPeak: score.counters.concentrationPeak
  }
}
```

### Why the wrapper constructs the payload

The shell deliberately does not receive net worth, profit, or other play-money amounts.

**Profit is not a learning score.**

The wrapper therefore forwards only the fields needed to evaluate financial decision-making.

### Adapter expectations

The adapter accepts:

```ts
{
  game: 'dealboard',
  mode: 'lite',

  judgement: number,

  skills: {
    research: number,
    skepticism: number,
    spread: number,
    calm: number,
    habits: number
  },

  counters?: {
    tabsOpened?: number,
    trapsAvoided?: number,
    prematureSells?: number,
    fees?: number,
    concentrationPeak?: number
  },

  quartersPlayed?: number,
  lessonsSeen?: string[]
}
```

Each skill has a maximum of 20 points.

### Skill mapping

| Deal Board skill | Shell skill |
|---|---|
| Research | Planning |
| Skepticism | Scam sense |
| Spread | Risk sense |
| Calm | Patience |
| Habits | Saving |

The headline judgement is normalised to a 0–1 quality score.

The current clear threshold is:

```ts
judgement >= 60
```

If a headline judgement is missing, the adapter can calculate it from the five skill values.

### Important financial-data rule

Never use net worth, profit, or play-money balance to calculate:

- Pillar completion.
- Quality.
- Happy Index.
- Overall learning progress.

The game should reward good decisions, not lucky market outcomes.

## 5.4 Case Files: Mohalla Detective — Financial Safety

**Location:** `src/pillar4/`

**Main component:** `src/pillar4/Pillar4.tsx`

**Host integration:** `src/host/wrappers/CaseFilesGame.tsx`

**Adapter:** `src/host/adapters/casefiles.ts`

Case Files is currently a self-contained application module rather than a standard `src/games/<folder>/index.tsx` game.

The shell wrapper supplies:

- Language.
- Avatar portrait.
- Exit callback.
- Completion handling.

The wrapper reads the Case Files status using:

```ts
getPillar4Status()
```

When the player exits, this status is passed to the shell adapter.

Finishing the Master Board does not immediately end the session. The player can continue reading the Playbook before leaving.

### Host interface

The internal Pillar 4 host interface is defined in:

`src/pillar4/host.tsx`

It is separate from the common `GameProps` interface.

```ts
export interface Pillar4Host {
  language: Lang
  avatarSrc?: string

  setLanguage: (language: Lang) => void
  onExit: () => void
  onComplete: () => void
}
```

### Result format

The shell adapter understands:

```ts
{
  status: 'locked' | 'in_progress' | 'complete',

  shieldPieces: (
    'protect' | 'verify' | 'pause'
  )[],

  diamonds: number,
  title: string,
  playbookReady: boolean,

  stage?: (
    'tutorial' |
    'case1' |
    'case2' |
    'case3' |
    'mystery' |
    'master'
  ),

  firstTryAccuracy?: number,
  lessonsSeen?: string[]
}
```

### Completion rules

The pillar is cleared when:

```ts
status === 'complete'
```

Quality is calculated from `firstTryAccuracy` when available. Otherwise, it is based on the number of shield pieces collected.

Partial progress uses the reported stage when available.

Diamonds are treated as rewards earned during the current play. The shell adds them to its wallet.

### Save-data isolation

Case Files maintains its own local state.

Do not directly modify the application's global game store or other pillars' save data.

Before changing persistence keys or reset behaviour, coordinate with the shell owner. The current reset integration should be verified before relying on it to clear every Case Files save.

# 6. What happens when a game completes?

The shell converts every game's result into one shared type:

`GameResult`, defined in `src/host/types.ts`.

The normalised result looks like:

```ts
interface GameResult {
  pillar: PillarId

  cleared: boolean
  quality: number
  partial: number

  skills: Partial<Record<Skill, number>>

  lessonsSeen: string[]

  joySignals: JoySignals

  rewards?: GameRewards

  raw: unknown
}
```

The fields mean:

| Field | Meaning |
|---|---|
| `pillar` | Which of the four pillars produced the result |
| `cleared` | Whether the player completed the pillar |
| `quality` | Quality of the performance, from 0 to 1 |
| `partial` | Progress toward completion, from 0 to 1 |
| `skills` | Normalised financial skills practised |
| `lessonsSeen` | Lessons encountered during the game |
| `joySignals` | Optional signals used by the Happy Index |
| `rewards` | Optional rewards such as diamonds and shield pieces |
| `raw` | Original game payload retained for logging and debugging |

The adapters are responsible for translating game-specific data into this common format.

**Game teams should not construct `GameResult` themselves unless the shell owner specifically asks them to.** Send the game's own payload through the integration wrapper.

# 7. Progress and completion

The shell uses the normalised result to update the player's progress.

The important concepts are:

- `cleared`: whether the pillar has been completed.
- `quality`: how well the player performed.
- `partial`: how far the player got without completing the pillar.

A cleared pillar contributes to overall progress.

A replay should not make a player's previously earned progress worse.

The exact progress and Happy Index calculations belong to the shell, not to individual game implementations.

Do not duplicate these calculations inside your game.

# 8. Happy Index and optional signals

The common interface defines:

```ts
export interface JoySignals {
  friendship?: number
  treatsBought?: number
  treatsSkipped?: number
  lentToFriends?: number
  scammed?: number
  restedOrBalanced?: number
}
```

These are optional signals.

They allow the shell to understand more than just whether the player won.

For example:

- Friendship can represent how well the player balanced relationships and money.
- Treats bought and skipped can represent a balance between saving and enjoying life.
- Lending can represent social financial decisions.
- Scams can represent exposure to risky situations.
- Restful or balanced decisions can represent healthier choices.

Send these signals only when your game can measure them meaningfully.

Do not invent values simply to improve the player's Happy Index.

# 9. Seeds, randomness, and replay behaviour

The host generates a seed using:

`src/host/seed.ts`

The seed is derived from the installation ID, pillar, and session seed salt.

The host passes the seed through `GameProps`.

For games that use the seed:

- Use it for gameplay randomness.
- Do not use unseeded `Math.random()` for gameplay-affecting decisions.
- Keep the same seed for a normal replay when the host provides the same seed.
- Do not use random outcomes to change difficulty unfairly.

**Current implementation note:** Not every game currently consumes the host seed. Deal Board receives it directly. Festival Showdown and Pocket Panic manage their own saved game state through their wrappers, and Case Files is self-contained.

Do not assume the same seed behaviour is already implemented across all four games.

# 10. Exit and completion behaviour

The game host protects each play session against duplicate completion.

The host checks that:

- A play session is active.
- The session has not already completed.
- The result is processed only once.

The wrapper should also prevent duplicate callbacks when the underlying game fires multiple events.

The current wrappers use a `sent` ref for this purpose.

### When should the game call completion?

Call the completion callback when:

1. The player reaches the final result/report.
2. The player exits before reaching the final result, if the wrapper treats that exit as a quit.

An early exit should not accidentally count as a successful completion.

A game should provide a clear way to leave without getting stuck.

# 11. Screen layout and input expectations

Games are mounted inside the application's game host.

The shell owns the outer application navigation and result flow. The game owns its internal gameplay UI.

The current configuration marks Plan, Save, and Invest as wide games:

```ts
export const WIDE_GAMES = [
  'plan',
  'save',
  'invest'
]
```

This means those games can use a wider layout while playing.

Build responsive layouts rather than assuming one fixed device size.

Recommended expectations:

- Mobile-first design.
- Support narrow phone screens.
- Do not depend on a fixed pixel height.
- Respect safe areas on notched devices.
- Make important controls reachable.
- Support mouse and touch.
- Provide keyboard-accessible controls.
- Do not make drag the only way to perform an action.

The game should remain usable when embedded inside the shell.

# 12. Offline and privacy requirements

These are application-wide requirements.

Every game must:

- Work offline after the application has loaded.
- Avoid requiring network access for ordinary gameplay.
- Avoid requiring a player sign-in.
- Avoid collecting personal information.
- Avoid real financial transactions.
- Avoid advertisements.
- Use fictional brands and fictional financial scenarios.
- Clearly communicate that game money is illustrative.

Money-related screens should include:

**"Made-up numbers. Real life is different."**

Do not introduce real investment recommendations or imply that the game's simulated outcomes predict real returns.

Audio is optional. If you add sound, provide an equivalent caption or visual cue.

# 16. Important implementation differences to resolve later

The following items are deliberately documented as current limitations rather than assumed features:

1. **Language:** The shared application currently exposes only `en`. Hindi and Telugu are not part of the current `Lang` type.
2. **Entry points:** The registry supports `index.tsx`, but current games are integrated through wrappers and configured component entries.
3. **Save game:** Pocket Panic is the configured Save game. Pay Run remains as a legacy implementation and adapter.
4. **Safety game:** Case Files currently lives in `src/pillar4/`, not `src/games/casefiles/`.
5. **Seed behaviour:** Deal Board receives the host seed. Other games currently manage their own saved state or use their own internal mechanisms.
6. **Progress model:** The adapters determine normalised quality and partial progress. The shell owns the final progress calculation.
7. **Reset behaviour:** Self-contained games must coordinate their persistence/reset behaviour with the shell owner.

These differences should be resolved through coordinated changes to the host contract—not by individual teams silently changing shared files.

---

# Final rule

**Build your game. Keep its implementation self-contained. Report results through the agreed integration interface. Let MoneyVerse handle progress, rewards, the Happy Index, and the overall player experience.**

If something in the host prevents your game from integrating correctly, contact the shell owner rather than changing shared application code independently.
